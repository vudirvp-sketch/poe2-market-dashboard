- **Site 1 analysis (line 328 — `setTabLocal(uiState.activeTab)`):** The effect syncs the store's persisted `uiState.activeTab` into local `tab` state on hydration. The `tab === "overview"` guard preserves the user's manual tab switches (`setTab` updates both local + store together, so once the user clicks a tab, `tab` diverges from "overview" and the sync is a no-op). Considered Recipe 1 (derive during render — eliminate local `tab` entirely), but rejected because of SSR/hydration safety: on the very first client render `storeHydrated` may still be false, so `uiState.activeTab` could be empty. Keeping a local `tab` state initialized to "overview" ensures the SSR HTML matches the first client render (both show "overview"), and the prev-guard syncs to the persisted value only after the store actually transitions. Applied Recipe 3 (adjust state during render with `prevStoreActiveTab` guard).
- **Site 2 analysis (line 387 — `setReferenceCurrency("")`):** The effect does TWO things on league change: (a) `setBaseCurrency(...)` (Zustand store action — does NOT trigger the rule per iter 122 insight) and (b) `setReferenceCurrency("")` (React `useState` setter — DOES trigger). The trigger is complex: `leagues`, `effectiveLeague`, `referenceCurrencies`, `safeBaseCurrencyApiId` are all in the deps array. Considered moving the entire effect to render-time, but rejected because calling Zustand `set` during render is a code smell (triggers store subscribers synchronously). Designed **Recipe 7 (split effect)**: extract the shared condition into `shouldResetForNewLeague()` (useCallback), keep the Zustand mutation in the effect (re-validates on every async input change), move the React `setState` to a render-time block keyed on `effectiveLeague` transition (fires once per league switch). Traced the semantics: (1) user switches league → `effectiveLeague` transitions → both halves fire → store + local state reset together; (2) `referenceCurrencies` arrives after `effectiveLeague` (async) → effect re-fires → `setBaseCurrency` may re-validate (idempotent — same league default values) → render-time block does NOT fire (no `effectiveLeague` transition) → local `referenceCurrency` stays at "" (already reset). No regression. The "user clicks '_default' in the dropdown" case is handled by the `onReferenceCurrencyChange` event handler (line 762) which calls `setReferenceCurrency("")` directly — the effect was never the primary path for that case.
- **Site 3 analysis (line 538 — `setLastUpdated(new Date())`):** The effect updates `lastUpdated` to "now" whenever any of `currenciesData`/`uniquesData`/`exchangeData` references change (new data arrived from React Query). Considered deriving `lastUpdated` from React Query's `dataUpdatedAt` timestamps (`currenciesFetchedAt` etc. — already destructured at lines 404/425/444), but rejected because it changes the UX: manual refresh (`handleRefresh` at line 528) calls `setLastUpdated(new Date())` for IMMEDIATE UI feedback (the `dataUpdatedAt` fields only update after the refetch resolves, which can take a second). Deriving from `dataUpdatedAt` would make the "Last updated: 0 seconds ago" indicator feel less responsive. Applied Recipe 3 with three prev-value guards (`prevCurrenciesData`, `prevUniquesData`, `prevExchangeData`) — preserves the exact original semantics: `lastUpdated` is set to `new Date()` on any data reference transition (with the `if (currenciesData || uniquesData || exchangeData)` guard ensuring we don't update when going from data → undefined, e.g. league switch clears the cache).
